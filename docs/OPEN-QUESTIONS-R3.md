## B 门禁与契约（DEC-41 / DEC-42 落地）

### Q-R3-4 门禁用什么载体【P0】

- 背景：DEC-41 定了"提交与合并两处设门禁"，但**载体没定**。三种做法的代价不同。
- 选项：
  - A) **原生 `.git/hooks` 脚本 + 安装脚本**：零依赖，但每台机器要跑一次安装（且 hook 不进版本库）
  - B) **`husky` + `lint-staged`**：随 `npm install` 自动装（但要加依赖，且只对 Web 侧自然）
  - C) **仓库根 `tools/` 脚本 + `git config core.hooksPath`**（把 hook 目录纳入版本库）★
  - D) A + CI（若后续启用 GitHub Actions，合并门禁交给 CI）
- ★建议：**C + D**（hook 脚本进版本库、`core.hooksPath` 一行配置；等有 CI 再把"合并门禁"交给 CI）。理由：不引入依赖、可审计、跨机器一致。
- 回答：D

### Q-R3-5 契约校验的基准怎么放【P0】

- 背景：DEC-10 定了"手写两份 + 校验比对"。我在 `design/03-layout-and-assets.md` §5 提了第三种东西：`content/contracts/snapshot.json`（**校验基准**，不是真源）。它可以自动发现"某一侧被改了"，但用错会变成"第三份事实源"（与 DEC-10 冲突）。
- 选项：
  - A) **采用快照基准**：改任一侧都必须同步改快照，门禁比对"TS ↔ 快照"和"C# ↔ 快照" ★
  - B) **不要快照**：门禁直接比对 TS ↔ C#（少了中间件，但两侧同时错就发现不了）
  - C) 不设门禁，靠人工纪律
- ★建议：**A**。理由：两侧同时被改错的概率不低（例如有人一次性把 `TaskType` 加错了地方），快照能兜住这种"一致地错"；而它的"第三份源"风险用一条纪律消除：**快照只能与某一侧同批修改**。
- 回答：你问的过于具体了 你自己定就好
