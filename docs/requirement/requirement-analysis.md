## 2 需求条目化

下面的 R-x 是对上表的展开，**没有一条超出原文语义**；括号里标注它的来源条目。

### R-1 从零新建架构（a）

- **含义**：新增代码不复制旧工程的目录结构；旧工程的**概念与经验**可以沿用，**文件布局**不可以照搬。
- **验收**：新仓库的目录布局能逐条说出「为什么这样分」，且理由不是"旧工程就是这样"。

### R-2 定位：教育类虚拟仿真软件（c）

- **含义**：用户是**学习者（学生）**，目的是**学 / 练 / 考**，不是工具软件、不是游戏、不是商业仿真系统。
- **对设计的直接约束**（由定位推导，非新增需求）：
  1. 内容必须**有教学结构**（章节 / 知识点 / 任务 / 考核），不能是自由沙盒；
  2. 操作要**可被评价**（有对错、有得分或进度反馈）；
  3. 面向课堂与机房，**部署与启动成本要低**（这直接支持 R-3）。
- **验收**：产品能回答"这节课学什么、怎么练、怎么算学会"。
- **缺口**：具体学科/设备对象、内容规模、用户角色分层 → Q-A 组。

### R-3 Web 端为默认交付形态（d）

- **含义**：**默认**（主目标）是浏览器可直接运行，不需要安装客户端。
- **验收**：在一台没有装任何本机软件的机器上，用浏览器打开链接即可用完主要功能。

### R-4 Electron 应用壳分支（d）

- **含义**：另有一条"app 壳"分支，把同一套 Web 产物装进桌面应用壳。
- **边界（原文"壳"字明示）**：Electron 只承担**外壳职责**（窗口、进程、可能的本地能力），**不得把平台相关逻辑渗进核心业务代码**（`AGENT.md` §2.3 已写死）。
- **验收**：核心业务代码里搜不到 Electron / Node 专有 API；壳层可被替换而不改业务。

### R-5 保留 SceneState 与 TaskType 概念（e）

- **含义**：这两个概念**沿用既有工程语义**，不改名、不重新发明。
- **已查明的事实**（见 `../research/04-reference-project-mcv.md`，含路径与行号）：
  - `SceneState` 是**枚举**，六个值 `Setup / Start / Login / Menu / UI / Roaming`，语义是**页面级导航状态机**（"一 Canvas 一状态"），只事件驱动、禁止拉取查询；
  - `TaskType` 是**枚举**，11 个值 `None / Purpose / Equipment / Principle / LineConnection / Training / Test / Info / Structure / Inspection / Exam`，语义是**当前展示的业务任务页签**，与 `TaskXxxPanel` + `TaskXxxController` + `TaskXxxData` 1:1 对应；
  - 两者都登记在 `Models/EnumAll.cs`，**只许往后追加**，`[InspectorName("中文")]` 与 JSON 写法是跨端契约。
- **已定（DEC-09）**：**原样继承全部枚举值**（`SceneState` 6 值、`TaskType` 11 值，含 `[InspectorName]` 中文），只许往后追加；序号与中文是跨端契约，逐字保持。详见 `../DECISIONS.md` DEC-09。

### R-6 三维交互按复杂度分流（f）

- **含义**：**复杂三维交互 → Unity**；**简单三维交互 → Three.js**。二者是**分工**，不是二选一（`AGENT.md` §2.1）。
- **这个需求真正的难点是"标准"**：哪些算复杂、哪些算简单，原文没给判定标准。
- **本文只给"判定的维度"，不给阈值**（阈值是决策，见 Q-B 组）：交互深度（是否有物理/装配/拆解/多步操作）、模型与材质复杂度、动画与骨骼、是否需要 Unity 生态能力（物理引擎、Timeline、Shader Graph）、加载体积与首屏预算、并行内容数量。
- **验收**：每个三维交互件在文档里能指认"归 Unity 还是 Three.js"，且理由是上列维度之一。

### R-7 参考工程只读（b）

- **含义**：`F:\Project\MCV_Module_0928`、`F:\Project\MCV_Module` 是**参考**，不是代码基线；不得在其中修改（`AGENT.md` §4）。
- **验收**：两工程的工作区状态不因本项目而变。

### R-8 需求极简 ⇒ 未覆盖决策必须先确认（流程性要求，来自 `AGENT.md` §4）

- **含义**：目录结构、通信方式、SceneState/TaskType 具体字段、Unity 与 Three.js 的边界判定标准，**都要先问**，不许自行拍板并当既定事实写进代码或文档。
- **验收**：`../OPEN-QUESTIONS.md` 中未回答的条目，不得在代码或文档里以"已决定"的语气出现。

## 3 不可动摇的约束（红线）

来自 `AGENT.md` §2（已由需求直接支撑），任何实现方案都不得违背：

1. 三维交互**分流**（复杂 Unity / 简单 Three.js），两条技术线**同时存在**。
2. `SceneState` / `TaskType` **保留**，不改名、不重新发明。
3. **Web 优先，Electron 为壳**，平台相关逻辑不得渗入核心业务代码。
4. **从零开始**：新增代码不得照搬旧工程目录结构。
