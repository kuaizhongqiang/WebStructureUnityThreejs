# 调研 03：集成与交付（Web 外壳 / Unity 模块 / Electron 壳）

> 读者：AI 与人｜状态：2026-10-12 v0｜性质：技术调研，**★ 是当时的建议值**。
> ⚠️ 本文的建议**已被 `../DECISIONS.md` 取代**：最终决定为 DEC-07（同页挂载 + `.jslib` 桥 + JSON）、DEC-08（真源在 Web 侧）、DEC-20 / DEC-32（Electron 同仓子目录 + 装本地 Web 产物）、DEC-21（无后端）、DEC-22（先本地验证）。冲突时以 `DECISIONS.md` 为准。

## 1 问题定义

R-3（Web 默认）+ R-4（Electron 壳）+ R-6（三维分流）三条需求交在一起，必然要在三个地方做决定：

1. **Web 外壳**长什么样、怎么组织页面；
2. **Unity 模块**怎么被装进 Web 页面、两边的边界在哪；
3. **状态与数据**由谁持有（单一真源在哪一侧）；
4. **Electron 壳**到底装什么。

## 2 目标形态（★建议）

```text
浏览器 / Electron 壳
└─ Web 主站（Vite 产物，静态托管）
   ├─ 教学外壳：页面、导航、任务（SceneState / TaskType 驱动）
   ├─ Three.js 模块：简单三维交互（内联渲染，同一 DOM 树）
   └─ Unity 模块：复杂三维交互（WebGL 产物，按需挂载）
```

- **一套 Web 产物同时服务浏览器与 Electron 壳**（壳只换容器，不换业务代码）——这是 R-4"壳"的最小成本实现。
- Unity 模块**按需加载**：只有进入需要复杂三维的 `TaskType` 时才拉 Unity 产物，否则首屏只有 Web 壳。

## 3 Unity 模块的挂载方式

| 方式 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **同页挂载** ★建议 | 页面上一个 `<div id="unity-canvas">`，用 Unity 的 `createUnityInstance()` 把画布挂进去；同一个 JS 运行时 | 通信最直接、无跨帧/跨域开销、UI 可整体控制 | Unity 崩溃会波及宿主页面；CSS 焦点/滚动需要处理 |
| `<iframe>` 隔离 | Unity 产物独立页面，用 `<iframe>` 内嵌 + `postMessage` | 隔离好、可独立部署/升级；一个页面要多个 Unity 实例时更干净 | 多一层消息封装；全屏/键盘输入要额外处理 |

**建议默认**：**同页挂载 + `.jslib` 桥**（`01-unity-line.md` §4）；若后续出现"多实例并存"或"独立部署"需求，再切 iframe，协议保持不变。

**加载体验要点**（教育软件首屏是硬指标）：
- 必须做**加载进度 + 可取消/可返回**，不能白屏干等；
- Unity 产物建议带内容哈希 + 长缓存，二次进入应近即时；
- 进入/退出 Unity 模块要**显式销毁**（`unityInstance.Quit()`），否则 WebGL 上下文与内存泄漏，切几次页面就崩。

## 4 通信协议（★建议草案，**待确认**）

原则（借鉴参考工程"事件驱动、禁止拉取查询"的红线）：

1. **消息一律 JSON**，含 `type` / `version` / `payload` / `seq` 字段；
2. **版本握手**：Web 与 Unity 模块启动时交换协议版本，不匹配就明确报错，不要静默降级；
3. **单向广播 + 事件订阅**，不提供"查询当前状态"的同步接口；
4. **权威状态只有一份**（见 §5），另一侧是投影。

消息方向示例（**形式待确认，不是已决定**）：

| 方向 | 类型示例 | 用途 |
|---|---|---|
| Web → Unity | `scene:load` / `task:switch` / `object:focus` / `ui:locale` | 下达当前场景与任务、聚焦某个部件、切换语言 |
| Unity → Web | `ready` / `progress` / `task:completed` / `score` / `error` | 就绪、加载进度、任务完成、成绩、异常 |
| 双向 | `sceneState:changed` / `taskType:changed` | 与 R-5 的枚举严格对应 |

## 5 单一真源归属（**必须拍板**）

三条路，各有后果：

| 方案 | 真源在哪 | 优点 | 风险 |
|---|---|---|---|
| **A. Web 侧为真源** ★建议 | Web 外壳持有当前 `SceneState` / `TaskType` / 数据；Unity 只做"被指令的渲染与交互"，回报结果事件 | 与 R-3"Web 默认"一致；Electron 壳零改动；Unity 侧不依赖后端 | Unity 模块必须有"无外壳也能跑"的降级（调试期） |
| B. Unity 侧为真源 | Unity 驱动状态，Web 是投影 | Unity 三维逻辑自洽 | 违背"Web 优先"；无 Unity 的页面（纯 Three.js 页）要另造一套状态 |
| C. 后端为真源 | 所有状态在服务端，双端各自同步 | 多端一致、可断点续学 | 必须有后端（当前**没有**）；离线/局域网部署受限 |

**建议默认 A**，并明确一条纪律：**Web 侧持有状态，但状态变更必须发事件通知 Unity，Unity 不得自己发明状态**（等价于参考工程"禁止拉取查询"的 Web 化写法）。

## 6 Electron 壳（R-4）

| 维度 | 选项 | 建议 |
|---|---|---|
| 装什么 | (a) 直接加载**线上 URL**；(b) 内嵌**本地打包的同一份 Web 产物** ★；(c) 拉起 **Unity Windows 单机版** | ★(b)：离线可用、与 Web 同一份代码；仅当 WebGL 性能不达标时启用 (c) |
| 版本 | `electron` 44.7.0（实测 latest） | 跟着主站产物版本走 |
| 边界纪律 | R-4 原文"壳" + `AGENT.md` §2.3：**平台相关逻辑不得渗入核心业务代码** | 壳内允许：窗口/菜单/文件、自动更新、启动参数；**禁止**：业务逻辑、三维实现差异分叉 |
| 代码隔离 | ★建议独立 `electron/` 目录 + 独立 `package.json`，业务代码零 `import electron` | 可通过 lint 规则（禁止从业务目录导入 electron）机械保证 |
| 分支形态 | "同仓分支"还是"同仓子目录" | **待确认** → Q-E5（原文只说"有分支"） |

## 7 交付形态与部署（★建议，待确认）

| 项 | 建议 | 理由 |
|---|---|---|
| 静态托管 | 单一静态站点（Windows Server / Nginx / IIS 均可），Web 包 + Unity 包同域 | 免跨域、免 COOP/COEP 折腾 |
| 域名/路径 | 支持子路径部署（如 `/sim/`） | 教育平台常挂在别的站点下 |
| 离线/局域网 | 全静态、无后端依赖 ⇒ 天然支持局域网部署 | 与"教育场景"匹配；但**成绩/进度落库需要后端**，见 Q-E2 |
| 数据 | 教学内容 JSON + 模型资源随包发布 | 与参考工程"JSON 为运行期唯一真源"一致 |
| 更新 | 内容与代码分离，内容可热更新 | 教学内容和模型会频繁改，不该每次重发整个包 |

## 8 风险清单（按严重度）

1. **浏览器基线过旧** ⇒ Unity WebGL（wasm）与 Three.js 现代产物**双双不可用**，整个技术路线要重定。→ Q-D4
2. **Unity WebGL 包体与首屏** ⇒ 若不从第一天做分包与压缩，后期无法补救。→ Q-C2
3. **中文全字库**在 WebGL 上的成本（TMP 不能动态补字）⇒ 包体显著膨胀。→ Q-C2
4. **双端资产不一致** ⇒ 同一设备在 Unity 与 Three.js 里长得不一样；必须靠"单一资产源 + sidecar 语义"约束。→ Q-C1
5. **没有测试体系**会重演参考工程的缺陷积压（`04-reference-project-mcv.md` §7.2.7）⇒ ★建议新项目保留自动化测试（单测 + 三维渲染冒烟）。
6. **版本控制现状**：仓库无 `.gitignore`，`NewStructureUnity/Library/` 等生成目录会被纳入 git（约 2.7 万文件）。→ Q-F1
7. **协议无版本号** ⇒ Web 与 Unity 模块独立升级后静默不兼容。→ §4 已列为强制项。
